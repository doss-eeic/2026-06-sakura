# Markdown解析の分離と入力補助の実装手順

状態：解析の分離はPR #22で完了。本ブランチでは、入力補助に先立って文脈付きの行解析を実装する。以下のEnter・Tab・番号プレビューの手順は実装予定と確認条件であり、実施結果ではない。

今回の作業は「既存解析の分離」から開始し、その完了後に「Enter補助」を実装する。
コマンドや描画クラスへ新しい構文判定を追加して、後から移動する進め方は採らない。

## 現段階の文脈解析

- `CMarkdownBlockParser::ParseLine(text, lineIndex, tabWidth, state)`へ、改行コードを除く論理行を先頭から順に渡す。文書先頭では状態を初期化する。
- タブ幅は呼び出し側のタイプ設定から渡す。原文位置はUTF-16オフセット、字下げは指定幅でタブを展開した列数として管理する。インデントコードの境界はコンテナの内容開始位置から4列とする。
- 明示的な接頭辞は、引用が`> `、箇条書きが`- `・`+ `・`* `、番号付きが数字と`. `。記号後の半角スペースを認識条件とする。
- タスクは箇条書きの直後にある`[ ]`・`[x]`を認識し、接頭辞に含める。チェックボックスの直後には空白・タブ・行末が必要。
- 番号は`unsigned int`の最大値の桁数まで読み、値も上限以下であることを確認する。上限を超える番号は通常の本文として扱う。
- 引用・リストの親子関係、継続行、空行、コードフェンス、インデントコード、見出し、水平線を判定し、行の種類・原文範囲・次行へ引き継ぐ状態を返す。
- この段階の利用箇所は解析テスト。編集コマンドとの接続は後続のEnter補助で行う。以下の計画にある`1)`等の追加記法も、現段階の認識条件とは区別する。

## 1. 目的と基本方針

- Enterでリスト・引用を継続し、空の項目でEnterを押すと一段抜ける。
- Tab／Shift+Tabでリスト項目の階層を変更する。
- 番号付きリストは本文を `1.` のまま書けるようにする。保存内容を表示番号に書き換えない。
- 番号プレビュー有効時は、編集中の論理行に元の記法、それ以外の行に計算した番号を表示する。
- 対象はMarkdown。`-`・`+`・`*` は番号なし、`1.`・`1)` は番号付き。Typstの `+` の意味は持ち込まない。
- CommonMarkのリスト・引用・コードブロック規則を基準とし、タスクリストを追加で扱う。

## 2. 有効化と既存設定

- 入力補助は「Markdown改行」「Markdownインデント」「Markdown逆インデント」の編集コマンドとして追加する。
- Markdownタイプの初期キー割り当てにEnter／Tab／Shift+Tabを登録する。共通のキー解決は変更せず、既存のタイプ別上書きを利用する。
- 対象外の文脈では、各コマンドから既存の通常改行・インデント処理を呼ぶ。キーを再送信して再帰させない。
- 番号プレビューには独立したタイプ別ON/OFF設定を追加する。新規MarkdownタイプはON、他タイプはOFFとし、ユーザーが変更できるようにする。
- コマンド実行・描画時にタイプ名や拡張子を調べて機能を有効化しない。
- 既存設定の更新では、カスタム割り当て・明示的な未割り当てを保護する。既存タイプへの導入は設定画面で明示的に選択できるようにし、新規初期値を勝手に上書きしない。
- 既存の太字・斜体・取り消し線の有効判定を整理する作業は、今回の入力補助とは別の変更として扱う。

## 3. Enterの動作

| 現在行・位置 | 動作 |
| --- | --- |
| `- 内容`／`+ 内容`／`* 内容` の末尾 | 同じ階層・同じ記号で次の項目を作る |
| `1. 内容` の末尾 | 次の項目を `1. ` で作る |
| `3. 内容` の末尾 | 開始番号3を残し、次の項目は `1. ` で作る |
| `1) 内容` の末尾 | 区切りを維持して `1) ` で作る |
| `- [x] 内容` の末尾 | 次の項目を `- [ ] ` で作る |
| `> 内容` の末尾 | 引用の深さを維持して `> ` を補う |
| `> - 内容` の末尾 | 引用とリストの両方を継続する |
| 項目本文の途中 | 右側の本文を次の項目へ移し、新しい項目の接頭辞を補う |
| 記号・字下げの途中、通常の文章、コードブロック内 | 既存の通常改行処理を使う |

### 空の項目でEnter

- 本文が空白のみの項目も空と判定する。タスクのチェックボックスは本文に数えない。
- 最上位の空リスト項目は、その行のリスト記号を消して終了する。
- ネストした空リスト項目は親階層へ一段戻す。親が番号付きか箇条書きかも考慮する。
- `> - ` はリストだけを抜けて `> ` にする。次のEnterで引用を抜ける。
- `> > ` のような空の多重引用は、一回につき引用を一段減らす。
- 空項目から抜ける操作自体では不要な空行を追加しない。
- 改行または階層を抜ける一操作を、一回のUndoで戻せるようにする。

## 4. Tab／Shift+Tabの動作

- リスト項目内では、カーソルが本文中にあっても項目単位で一段深く／浅くする。
- 項目に属する本文の続き行・子リストも一緒に移動し、内部の相対字下げを保つ。
- 深くする場合は直前の同階層項目の子にする。親にできる項目がない場合は変更しない。
- 最上位でのShift+Tabは階層変更なしとし、項目記号を誤って消さない。
- 字下げ量は固定の2文字などで決めず、親項目の本文開始列と周囲の構造から求める。`- ` と `10. ` の記号幅の違い、タブの構文上の展開幅を考慮する。
- 複数行選択では触れている項目群とその子をまとめて扱い、同じ子を二重に移動しない。選択終端が次の行頭なら、その次行は含めない。
- 通常文章・引用だけの行・コードブロック内・矩形選択では既存のTab／逆インデント動作を使う。
- Enterの矩形選択・複数項目にまたがる選択も既存動作に委譲する。単一項目内の通常選択は削除後の位置で改行を計算する。

## 5. 解析の設計

完全なMarkdown文書のASTは作らず、入力補助と番号計算に必要なブロック情報を持つ。

### 配置と責務

以下のファイル名は新設する際の案。構文解析を `sakura_core/parse/markdown/` に集約する。

| 配置 | 責務 |
| --- | --- |
| `parse/markdown/MarkdownTypes.h` | 記号種別、原文範囲、ブロック状態、親子関係、強調属性などの共通データ型 |
| `parse/markdown/CMarkdownBlockParser.h/.cpp` | 字下げ・引用・リスト・タスク・コードフェンス・段落境界を解析する |
| `parse/markdown/CMarkdownInlineParser.h/.cpp` | 太字・斜体・取り消し線、エスケープ、コードスパン、リンク先の除外を解析する |
| `view/CMarkdownEmphasis.h/.cpp`（既存） | 文書の論理行を解析へ渡し、描画用キャッシュと原文位置から属性への参照を管理する |
| `cmd/CViewCommander_Markdown.cpp`（既存） | 解析結果とカーソル・選択状態から編集内容を決め、既存の編集／Undo機構で適用する |
| `view/figures/CFigureStrategy.cpp` 等（既存） | 受け取った属性からフォントを選び描画する |

### 依存方向

```text
編集コマンド ── 文書の論理行 ──→ Markdown解析 ──→ 構造・原文範囲
      └── 解析結果から編集操作を決定 ──→ 文書編集・Undo

描画用アダプター ── 文書の論理行 ──→ 同じMarkdown解析
      └── 属性・原文範囲をキャッシュ ──→ フォント選択・描画
```

- 解析器は行文字列・前方の解析状態を受け取り、構造を返す。文書の書き換えは行わない。
- 解析器から `CViewCommander`、`CEditView`、フォント、キー設定、タイプ設定を参照しない。
- 有効化するかどうかは呼び出し側が判断する。解析器はタイプ名・拡張子を知らない。
- 解析結果の位置は原文のUTF-16オフセットで返す。字下げの列数とは分け、画面のピクセル座標は持ち込まない。列計算に使うタブ幅は呼び出し側から値として渡す。
- 解析結果に長寿命の文書ポインターや借用文字列を保持しない。キャッシュの寿命・更新は呼び出し側で管理する。
- 「次に `1. ` を挿入する」「空項目から抜ける」は編集方針であり、解析器には入れない。

### 返す情報

1. **行頭解析**：字下げ、引用の各段、リスト記号、元の番号と区切り、タスク記号、本文開始位置を取得する。
2. **ブロック状態**：コードフェンス、インデントコード、リスト階層、項目の継続行、リストの開始・終了を追う。
3. **項目情報**：親項目、同階層の先行項目、所属する論理行範囲、開始番号・表示番号を求める。

- 空行だけで必ず別リストと判定しない。空行を含むリスト、引用内のリスト、番号区切りや箇条書き記号の変更も扱う。
- `---` 等の水平線、本文中の数字、コード内の記号をリストと誤認しない。
- 編集処理と番号プレビューが同じ解析結果を使う。まず正しさを確認し、その後に変更行より前の安全な境界から再解析するキャッシュを導入する。
- `CViewCommander_Markdown.cpp` の `IndentLength`／`ListMarkerLength` と、引用・フェンス等の認識処理を棚卸しし、構文を認識する処理はBlockParserへ移す。挿入する文字列の生成・URLのエスケープ等は編集側に残す。
- `CMarkdownEmphasis::Parse` はInlineParserへ、`ScanBlock` とコードフェンスの状態はBlockParserへ移す。
- 描画側の `Prepare` は文書の読み出しとキャッシュ管理の窓口として残すが、記号やフェンスを独自に解釈しない。
- 共通型の変更は呼び出し側とテストにも反映する。移行用の委譲関数を残す場合も、元の解析実装を複製しない。

## 6. 番号プレビューの設計

- 同じ番号付きリストの先頭の数値を開始番号として、同階層の項目だけを数える。子リストは独立して数える。
- 本文が `1.`・`1.`・`1.` でも、非編集行には `1.`・`2.`・`3.` と表示する。`1)` も区切りを保つ。
- 編集行はカーソルがある論理行とする。折り返された部分も同じ論理行として元の番号を表示する。
- 保存・コピー・検索・マクロ・Undoは常に元の本文を対象にする。プレビュー切り替えだけでは文書を更新状態にしない。
- `1.` → `10.` のように桁数が変わるため、番号の描画差し替えだけで済ませず、表示幅と本文位置の対応を設計する。
- 対応表をクリック位置、カーソル、選択範囲、横スクロール、折り返しに適用する。表示上だけ増えた数字の領域は元の番号トークンへ対応付ける。
- カーソル移動時は旧編集行と新編集行を再描画する。分割ペインごとに編集行を管理し、解析結果は共有できるようにする。

## 7. 最初からの作業手順

### 手順1：mainを基準に作業を開始する

1. 作業ツリーと既存のローカル変更を確認し、ユーザーの変更を保持する。
2. `git fetch origin` で更新し、表示機能を含む前提の変更がmainに入っていることを確認する。
3. mainを更新して `refactor/markdown-parser` ブランチを作る。
4. `help/markdown-editing.md`、既存のMarkdown編集処理、強調解析、関連テストを読み、現在の振る舞いを把握する。

### 手順2：解析の入出力を定義する

1. 第5節の配置で共通型とBlockParser／InlineParserのインターフェースを用意する。
2. 最初は既存実装が返せる情報を移し、Enter用の新しい動作は追加しない。
3. 行頭の記号認識と、文書の文脈を含めたブロック判定を区別する。明示的な既存編集コマンドの動作を、描画用判定へ置き換えた結果として変えないようにする。

### 手順3：既存解析を移し、利用箇所を切り替える

1. リスト・引用等の認識をBlockParserへ、強調記法の解析をInlineParserへ移す。
2. コードフェンス判定はBlockParserに一本化する。
3. 既存編集コマンドをBlockParserの結果を使う形に変更する。
4. `CMarkdownEmphasis` を新しい解析器へのアダプターに変更し、フォント選択や画面側のキャッシュはview層に残す。
5. 元の構文判定の重複実装を削除し、表示・編集側に新たな判定をコピーしていないことを確認する。
6. Visual Studioの本体／テストプロジェクトとフィルター、新規ソースのCMake取り込みを確認・更新する。

### 手順4：分離だけの変更を確認する（PR A）

1. 既存の解析テストは新モジュールを直接呼ぶように移す。描画キャッシュ・フォントのテストはview側に残す。
2. 既存リスト・引用・タスク・フェンスの認識には、移動前の振る舞いを保つ回帰テストを用意する。
3. 認識の不具合を見つけた場合は、単なる移動と混ぜず、再現例と仕様変更を明示した別コミットで修正する。
4. include、ソース登録、依存方向、差分をソース上で確認する。
5. 依頼者によるビルド・既存の編集と強調表示の確認結果を記録する。
6. 「Markdown解析の分離」としてmain向けのPRを作る。この段階でEnterの動作を変更しない。

完了条件：リスト・コード・強調の構文判定が専用モジュールにあり、既存の編集と表示がそこを利用していること。移動による意図しない挙動変更がないこと。

### 手順5：Enterに必要なブロック情報を拡張する

1. PR Aのmainへの取り込み後、最新mainから `feat/markdown-smart-enter` を作る。
2. BlockParserへ親項目・本文継続行・引用階層・コード内判定を追加する。
3. リスト内の字下げを一律にインデントコードと扱わず、親の本文開始列から相対的に判定する。
4. 空行を含むリスト、引用内のリスト、水平線との区別など、Enterに必要な構造をテストで確認する。
5. 文脈が不明なケースは補完しないと判断できる結果を返し、推測で文書を変更しない。

### 手順6：Markdown改行コマンドを登録する

1. `Funccode_x.hsrc` に空いている機能番号を追加する。
2. `CViewCommander.h`／`.cpp` に宣言とディスパッチを追加し、実装を `CViewCommander_Markdown.cpp` に置く。
3. 機能一覧、編集禁止判定、日英中のリソースを既存Markdownコマンドと同様に登録する。編集禁止配列の番号順も確認する。
4. コマンドは解析結果を参照する。ここにリストやフェンスを識別する正規表現・文字走査を新設しない。

### 手順7：Enterによる文書変更を実装する

1. まず通常の項目末尾で、改行＋同階層の接頭辞を挿入する。
2. 番号付きは次も `1.`／`1)`、タスクは未完了、引用の深さと箇条書き記号は維持する。
3. 次に本文途中での分割と、単一項目内の選択削除後の改行に対応する。
4. 空項目での一段退出を追加する。引用＋リストは内側から一段ずつ抜ける。
5. 通常文章・コード内・記号途中・対象外の選択は既存の改行処理に委譲する。キー再送信は使わない。
6. 文書の改行コードを使い、自動インデントを二重に適用しない。
7. 選択削除・接頭辞挿入・カーソル移動を一操作として既存Undo機構に記録する。読み取り専用の編集禁止も維持する。

### 手順8：タイプ別キー割り当てと説明を整える

1. `CType_Markdown.cpp` の新規初期設定にEnter→Markdown改行を追加する。
2. 共通キー解決や実行時にMarkdown名・拡張子の判定を追加しない。
3. 既存タイプは［タイプ別設定 → ショートカット］でEnterへ割り当てる手順を記載する。既存のカスタム割り当ては変更しない。
4. 通常改行へ戻す設定手順も `help/markdown-editing.md` に記載する。

### 手順9：Enter補助の確認と公開（PR B）

1. 第3節の全入力例、親の種類が異なる入れ子、本文途中、空項目、コード内を回帰テストで扱う。
2. CRLF／LF、選択、Undo／Redo、読み取り専用、他タイプの通常Enterを確認する。
3. 依頼者によるビルド・実行結果と、エージェントによるソース確認を分けて記録する。
4. リモートを更新し、mainとの差分を確認する。PRテンプレートに沿って「Markdown改行補助」のPRをmain向けに作る。

完了条件：第3節のEnter動作を満たし、解析が専用モジュールに保たれ、既存のキー設定・通常改行・Undoを損なわないこと。

## 9. 確認条件一覧

- 解析：記号全種、`1.`／`1)`、任意の開始番号、混在した親子リスト、引用、空行、タスク、フェンス、インデントコード、水平線。
- 入力：行頭／途中／末尾、空項目、通常選択／矩形選択、CRLF／LF、日本語、折り返し、読み取り専用、Undo／Redo。
- 階層：続き行と子リストの追従、番号の桁数に応じた字下げ、親のないTab、最上位のShift+Tab。
- 表示：9→10・99→100、開始番号3、入れ子、途中項目の追加削除、カーソル移動、選択・コピー・検索、横スクロール、分割ペイン。
- 設定：他タイプでの通常Enter／Tab、カスタム割り当ての保持、プレビューOFF、設定保存・再起動。
- 解析と編集結果には回帰テストを追加する。ビルド・アプリ起動は依頼者の実施を前提とし、ソース確認と実行結果を分けて記録する。
